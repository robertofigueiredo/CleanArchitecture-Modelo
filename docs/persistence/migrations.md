# Migrations

## Commands

Run from the repository root — `DbContext` lives in `Infrastructure`, the startup project (for
configuration/connection string resolution) is `Web.Api`:

```bash
dotnet ef migrations add <Name> --project src/Infrastructure --startup-project src/Web.Api
dotnet ef database update --project src/Infrastructure --startup-project src/Web.Api
```

`Microsoft.EntityFrameworkCore.Tools` is already referenced by `Web.Api`
(`Directory.Packages.props`), so `dotnet ef` works without any extra setup once you're in the
repo root.

## When to add a migration

Any change to an `IEntityTypeConfiguration<T>`, a new `DbSet<T>` on `ApplicationDbContext`, or a
change to an entity's persisted shape needs a matching migration — add it in the same PR as the
model change, not as a follow-up. Name it after what changed
(`20240811190111_Create_Database` is the existing example — a timestamp prefix generated by
`dotnet ef`, then a descriptive suffix).

## How migrations are applied

```csharp
// src/Web.Api/Extensions/MigrationExtensions.cs
public static void ApplyMigrations(this IApplicationBuilder app)
{
    using IServiceScope scope = app.ApplicationServices.CreateScope();
    using ApplicationDbContext dbContext = scope.ServiceProvider.GetRequiredService<ApplicationDbContext>();
    dbContext.Database.Migrate();
}
```

Called from `Program.cs` **only** `if (app.Environment.IsDevelopment())`. There is no dedicated
migration worker/service, and migrations are **not** automatically applied in any non-Development
environment — applying migrations against staging/production is an out-of-band operator action
(`dotnet ef database update`) today. If a new project needs automatic migration-on-deploy in other
environments, that's a deliberate addition to make (e.g. a startup migration step gated by an
explicit environment/flag check, or a dedicated migration job), not something to assume already
happens.

## Reviewing a generated migration

`dotnet ef migrations add` generates three files per migration
(`<Timestamp>_<Name>.cs`, `<Timestamp>_<Name>.Designer.cs`,
`ApplicationDbContextModelSnapshot.cs` updated) — always inspect the generated `Up`/`Down` methods
before committing:

- Confirm the snake_case names match expectations (`EFCore.NamingConventions` should already
  handle this — see [persistence/database.md](./database.md#naming-convention)).
- Confirm indexes/foreign keys/constraints you intended are actually present (`HasIndex`,
  `HasForeignKey`, `IsUnique()` in the configuration should show up as `migrationBuilder.CreateIndex`
  with the right uniqueness/columns).
- For a destructive change (dropping/renaming a column, narrowing a type), check the generated
  `Down` method and consider whether existing data needs a manual backfill step — EF Core does not
  write data-migration logic for you.

## Applying migrations locally

```bash
docker compose up          # starts postgres (+ web-api, seq)
dotnet ef database update --project src/Infrastructure --startup-project src/Web.Api
```

or simply run `src/Web.Api` in the `Development` environment against a running Postgres — 
`app.ApplyMigrations()` applies any pending migration automatically on startup in that environment.
